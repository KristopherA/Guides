AGM WI-FI SURVEY SENSOR
Raspberry Pi 3 Model B v1.2 + WiFi Explorer Pro
Setup Guide and Field Procedure
============================================================

PURPOSE
=======

This guide describes how to build and use a Raspberry Pi 3 Model B v1.2
as a fixed Wi-Fi survey and monitoring sensor for an AGM or similar event.

The Raspberry Pi is NOT intended to replace WiFi Explorer Pro.

Use the tools together:

  Raspberry Pi sensor
    - Fixed observation point
    - Long-duration passive Wi-Fi monitoring
    - Timestamped RF observations
    - Active connectivity tests on an authorized AGM WLAN
    - Evidence for troubleshooting incidents after the event

  Mac + WiFi Explorer Pro
    - Walking survey
    - Detailed interactive RF analysis
    - Coverage checks at defined survey points
    - 6 GHz analysis when supported by the Mac
    - Immediate investigation when a Pi sensor detects a problem

The Pi 3 built-in Wi-Fi is 2.4 GHz only. For a useful AGM survey, use
supported external USB Wi-Fi adapters for passive 2.4/5 GHz monitoring
and active client testing.

This guide intentionally excludes active wireless attack techniques such
as deauthentication, impersonation, credential capture, or disruption.
Use passive monitoring and normal client connectivity testing only on
networks you are authorized to assess.


============================================================
1. RECOMMENDED SENSOR DESIGN
============================================================

Recommended layout:

                         AGM Wi-Fi

                    AP1 )))  AP2 )))
                        \     /
                         \   /
                     +-----------+
                     | Delegates |
                     +-----------+

                         RF

                    +-------------+
                    | Raspberry Pi|
                    | Survey Node |
                    +-------------+
                      |    |    |
                      |    |    +-- USB Wi-Fi #2
                      |    |        Active client tests
                      |    |
                      |    +------- USB Wi-Fi #1
                      |             Passive/Kismet
                      |
                      +------------ Ethernet
                                    Management/upload

MacBook:
  WiFi Explorer Pro
  Walking survey and detailed investigation


Recommended interface roles:

  eth0
    Management access to the Pi.

  wlan0
    Pi built-in 2.4 GHz Wi-Fi.
    Leave unused, disable, or retain as an emergency management interface.

  wlan1
    USB adapter with Linux monitor-mode support.
    Used by Kismet for passive monitoring.

  wlan2
    USB adapter used as a normal client.
    Connected to the AGM Wi-Fi for active health tests.


============================================================
2. HARDWARE
============================================================

Required:

  Raspberry Pi 3 Model B v1.2
  Reliable 5 V / 2.5 A power supply
  High-quality microSD card, 32 GB or larger
  Ethernet cable
  Mac running WiFi Explorer Pro

Strongly recommended:

  USB Wi-Fi adapter #1
    Must support Linux monitor mode.
    Prefer a chipset with well-supported in-kernel Linux drivers.

  USB Wi-Fi adapter #2
    Used as a normal Wi-Fi client.
    Dual-band 2.4/5 GHz preferred.

Optional:

  USB Ethernet adapter
  USB-powered hub
  Small USB SSD for lengthy packet/log retention
  Short USB extension cables to physically separate Wi-Fi adapters
  Second or third Raspberry Pi sensor for additional venue locations


IMPORTANT:

Do not purchase a USB Wi-Fi adapter based only on marketing terms such as
"AC1200" or "Wi-Fi 6."

Verify:

  - Exact chipset
  - Linux kernel driver
  - Monitor-mode support
  - 2.4 GHz support
  - 5 GHz support
  - ARM64 compatibility

6 GHz monitoring should be performed with a modern supported survey device,
such as the Mac running WiFi Explorer Pro. Do not make the Pi 3 the
authoritative 6 GHz survey platform.

7. IDENTIFY THE WI-FI ADAPTERS
============================================================

Connect the passive USB Wi-Fi adapter.

Run:

  lsusb

  iw dev

  ip -br link

Record:

  Interface name
  USB chipset
  Driver

Determine driver:

  ethtool -i wlan1

Replace wlan1 with the actual interface name.

Connect the second USB Wi-Fi adapter and repeat.

Example target:

  wlan1 = passive monitoring
  wlan2 = active AGM Wi-Fi client


============================================================
8. PREVENT INTERFACE NAME CONFUSION
============================================================

Record MAC addresses:

  ip -br link

For each adapter:

  cat /sys/class/net/wlan1/address
  cat /sys/class/net/wlan2/address

Record these values in the survey notes.

Example:

  PASSIVE_MONITOR_MAC=aa:bb:cc:dd:ee:01
  ACTIVE_CLIENT_MAC=aa:bb:cc:dd:ee:02

Always verify interface assignments after a reboot:

  iw dev
  ip -br link


============================================================
9. TEST MONITOR MODE
============================================================

Do this before the AGM.

Stop NetworkManager from trying to manage the passive interface if
NetworkManager is present:

  sudo nmcli device set wlan1 managed no

Check:

  nmcli device status

Bring down the interface:

  sudo ip link set wlan1 down

Set monitor mode:

  sudo iw dev wlan1 set type monitor

Bring it back up:

  sudo ip link set wlan1 up

Verify:

  iw dev wlan1 info

Expected:

  type monitor

Test passive reception:

  sudo tcpdump -i wlan1 -c 20

Restore managed mode if required:

  sudo ip link set wlan1 down
  sudo iw dev wlan1 set type managed
  sudo ip link set wlan1 up

If monitor mode fails, investigate the USB adapter chipset and driver.


============================================================
10. INSTALL KISMET
============================================================

Prefer a current packaged Kismet build rather than compiling Kismet on a
Raspberry Pi 3.

Kismet explicitly notes that modern C++ compilation can be too resource
intensive for a Raspberry Pi 3.

First try the Raspberry Pi OS/Debian repository:

  sudo apt update
  sudo apt install -y kismet

Check:

  kismet --version

If the distribution version is old, use the Kismet package repository that
matches the exact Debian/Raspberry Pi OS base release.

Do NOT mix repositories intended for different Debian releases.

Kismet current documentation:

  https://www.kismetwireless.net/docs/
  https://www.kismetwireless.net/packages/

Add the administrative user to the Kismet group:

  sudo usermod -aG kismet ADMINUSER

Reboot:

  sudo reboot

After reconnecting:

  groups

Confirm "kismet" appears in the group list.

============================================================
12. INITIAL KISMET TEST
============================================================

Verify the passive adapter:

  iw dev

Start Kismet manually for the first test:

  kismet -c wlan1

Open the Kismet web interface from an authorized management workstation.

Default Kismet web service commonly listens on:

  http://PI-IP-ADDRESS:2501

Determine the Pi Ethernet IP:

  hostname -I

On first access, configure the Kismet web-interface credentials.

Confirm:

  - wlan1 is detected
  - packets are being received
  - access points are appearing
  - expected AGM/test SSIDs can be seen
  - 2.4/5 GHz bands expected from the adapter are visible

Stop the test with Ctrl+C.


============================================================
13. KISMET CONFIGURATION
============================================================

Configuration paths may vary by package version.

Locate them:

  kismet --help | head -50

  find /etc -maxdepth 2 -iname '*kismet*' -print 2>/dev/null

Common locations include:

  /etc/kismet/kismet.conf
  /etc/kismet/kismet_site.conf

Prefer site/local configuration files so package upgrades do not overwrite
custom settings.

Create a survey-specific configuration if supported by the installed
version.

Important configuration goals:

  - Capture source = passive USB Wi-Fi adapter
  - Web UI accessible only from the authorized management network
  - Log files written to /var/log/agm-wifi/kismet
  - Automatic startup
  - Log rotation/retention planned before the event

Do not expose the Kismet web interface to an untrusted conference WLAN.


============================================================
14. ACTIVE WI-FI CLIENT
============================================================

The second USB adapter should connect normally to the AGM WLAN.

This interface is not placed in monitor mode.

Example with NetworkManager:

  sudo nmcli radio wifi on

List interfaces:

  nmcli device status

List available WLANs:

  nmcli device wifi list ifname wlan2

Connect:

  sudo nmcli device wifi connect "AGM-SSID" \
    password "WIFI-PASSWORD" \
    ifname wlan2

IMPORTANT:

Do not place Wi-Fi passwords directly into long-lived shell scripts or
survey reports.

For enterprise 802.1X Wi-Fi, configure the connection using the
organization's approved credentials and authentication method.

Verify:

  nmcli connection show --active

  ip addr show wlan2

  ip route

Test:

  ping -c 4 GATEWAY-IP

  dig example.com

  curl -I https://example.com


============================================================
15. ACTIVE HEALTH TEST SCRIPT
============================================================

Create:

  sudo mkdir -p /opt/agm-wifi
  sudo mkdir -p /var/log/agm-wifi/health

Create the script:

  sudo nano /opt/agm-wifi/wifi-health.sh

Paste:

------------------------------------------------------------
#!/bin/bash

set -u

INTERFACE="${INTERFACE:-wlan2}"
TARGET="${TARGET:-1.1.1.1}"
DNS_NAME="${DNS_NAME:-example.com}"
HTTP_URL="${HTTP_URL:-https://example.com}"
LOG_DIR="${LOG_DIR:-/var/log/agm-wifi/health}"

mkdir -p "$LOG_DIR"

DATESTAMP="$(date '+%Y-%m-%d')"
TIMESTAMP="$(date --iso-8601=seconds)"
LOGFILE="$LOG_DIR/wifi-health-$DATESTAMP.csv"

if [ ! -f "$LOGFILE" ]; then
    echo "timestamp,interface,ssid,bssid,signal_dbm,frequency_mhz,ip_address,gateway,ping_loss_percent,ping_avg_ms,dns_seconds,http_seconds,http_code" > "$LOGFILE"
fi

SSID="$(iw dev "$INTERFACE" link 2>/dev/null | awk -F': ' '/SSID:/ {print $2; exit}')"
BSSID="$(iw dev "$INTERFACE" link 2>/dev/null | awk '/Connected to/ {print $3; exit}')"
SIGNAL="$(iw dev "$INTERFACE" link 2>/dev/null | awk '/signal:/ {print $2; exit}')"
FREQ="$(iw dev "$INTERFACE" link 2>/dev/null | awk '/freq:/ {print $2; exit}')"

IPADDR="$(ip -4 -o addr show dev "$INTERFACE" 2>/dev/null | awk '{print $4}' | cut -d/ -f1 | head -1)"
GATEWAY="$(ip route 2>/dev/null | awk -v dev="$INTERFACE" '$1=="default" && $0 ~ dev {print $3; exit}')"

PING_OUTPUT="$(ping -I "$INTERFACE" -c 5 -W 2 "$TARGET" 2>/dev/null || true)"

PING_LOSS="$(printf '%s\n' "$PING_OUTPUT" | awk -F', ' '/packet loss/ {gsub("% packet loss","",$3); print $3}')"
PING_AVG="$(printf '%s\n' "$PING_OUTPUT" | awk -F'/' '/rtt|round-trip/ {print $5}')"

DNS_TIME="$(curl --interface "$INTERFACE" -o /dev/null -sS \
    --max-time 10 \
    -w '%{time_namelookup}' \
    "https://$DNS_NAME/" 2>/dev/null || echo "FAIL")"

HTTP_RESULT="$(curl --interface "$INTERFACE" -o /dev/null -sS \
    --max-time 15 \
    -w '%{time_total},%{http_code}' \
    "$HTTP_URL" 2>/dev/null || echo "FAIL,000")"

HTTP_TIME="$(printf '%s' "$HTTP_RESULT" | cut -d, -f1)"
HTTP_CODE="$(printf '%s' "$HTTP_RESULT" | cut -d, -f2)"

echo "$TIMESTAMP,$INTERFACE,$SSID,$BSSID,$SIGNAL,$FREQ,$IPADDR,$GATEWAY,$PING_LOSS,$PING_AVG,$DNS_TIME,$HTTP_TIME,$HTTP_CODE" >> "$LOGFILE"
------------------------------------------------------------

Make executable:

  sudo chmod 750 /opt/agm-wifi/wifi-health.sh

Set ownership:

  sudo chown root:kismet /opt/agm-wifi/wifi-health.sh

Test:

  sudo INTERFACE=wlan2 /opt/agm-wifi/wifi-health.sh

Inspect:

  sudo tail -5 /var/log/agm-wifi/health/wifi-health-$(date '+%Y-%m-%d').csv

16. CREATE SYSTEMD HEALTH TEST SERVICE
============================================================

Create:

  sudo nano /etc/systemd/system/agm-wifi-health.service

Paste:

------------------------------------------------------------
[Unit]
Description=AGM Wi-Fi active health test
After=network-online.target
Wants=network-online.target

[Service]
Type=oneshot
Environment=INTERFACE=wlan2
Environment=TARGET=1.1.1.1
Environment=DNS_NAME=example.com
Environment=HTTP_URL=https://example.com
ExecStart=/opt/agm-wifi/wifi-health.sh
------------------------------------------------------------

============================================================
24. INCIDENT PROCEDURE
============================================================

When a user reports a Wi-Fi problem:

STEP 1 - RECORD THE EXACT TIME

  Example:

    10:43:17 MDT

STEP 2 - RECORD LOCATION

  Example:

    A05 - Main hall centre

STEP 3 - RECORD SYMPTOM

  Examples:

    Cannot join Wi-Fi
    Connected but no Internet
    Very slow
    Video call failing
    Website inaccessible
    Repeated disconnects

STEP 4 - CHECK PI ACTIVE TESTS

  On sensor:

    tail -20 /var/log/agm-wifi/health/wifi-health-$(date '+%Y-%m-%d').csv

Look for:

  Signal change
  BSSID change
  Packet loss
  Gateway reachability
  DNS latency
  HTTP latency
  HTTP failures

STEP 5 - CHECK PASSIVE SENSOR

Use Kismet to examine the same timestamp.

Look for:

  AP disappearance
  BSSID changes
  Channel changes
  Increased nearby AP count
  Strong competing APs
  Other unusual RF changes

STEP 6 - USE WIFI EXPLORER PRO

Go to the affected survey point with the Mac.

Record:

  Current AP/BSSID
  Band
  Channel
  Width
  RSSI
  SNR/noise where available
  Co-channel APs
  Overlapping networks

STEP 7 - TEST NORMAL CLIENT FUNCTIONS

From an authorized client:

  Association
  DHCP
  Gateway
  DNS
  Internet HTTPS

STEP 8 - CLASSIFY

Possible categories:

  COVERAGE
    Poor RSSI/SNR.

  RF CONTENTION
    Good signal but crowded channel or airtime problems.

  AP/RADIO
    AP/BSSID vanished or changed unexpectedly.

  DHCP
    Client associates but does not obtain valid network configuration.

  DNS
    IP connectivity works but name resolution fails or is very slow.

  UPSTREAM
    WLAN functions but Internet path is degraded.

  APPLICATION
    Network tests are healthy but a particular application fails.

  UNKNOWN
    Insufficient evidence.

STEP 9 - DOCUMENT ACTION

Examples:

  Venue contacted
  AP restarted by venue
  Channel changed
  Upstream issue escalated
  No infrastructure change made
  Continued monitoring

26. INTERPRETING COMMON RESULTS
============================================================

CASE 1:

  RSSI: good
  Gateway latency: poor
  Packet loss: high

Likely areas:

  Wi-Fi contention
  AP/client capacity
  RF interference
  WLAN infrastructure


CASE 2:

  RSSI: poor
  Packet loss: high

Likely area:

  Coverage or local RF conditions


CASE 3:

  RSSI: good
  Gateway: good
  DNS: poor

Likely area:

  DNS


CASE 4:

  RSSI: good
  Gateway: good
  DNS: good
  Internet: poor

Likely areas:

  Internet uplink
  firewall/proxy
  upstream congestion


CASE 5:

  Expected BSSID disappears from Kismet

Likely areas:

  AP reboot
  radio restart
  AP failure
  configuration change


CASE 6:

  BSSID changes but service remains healthy

Possibilities:

  Normal roaming
  AP steering
  WLAN controller behavior

Do not treat every BSSID change as a fault.

31. RECOMMENDED METRICS
============================================================

Do not rely on a single RSSI threshold.

Collect trends.

Useful metrics:

  RSSI
  BSSID
  Channel
  Frequency
  AP visibility
  Packet loss
  Gateway latency
  DNS time
  HTTPS response time

Useful warning indicators:

  Expected AP disappears
  Signal changes sharply at a fixed sensor
  Sustained packet loss
  Large increase in gateway latency
  DNS failures
  HTTPS failures
  BSSID/channel changes during incidents

Fixed sensors are especially valuable for detecting CHANGE.


============================================================
32. WHAT THE PI CANNOT PROVE
============================================================

A fixed Pi sensor does not replace:

  Professional predictive RF design
  Dedicated spectrum analysis
  WLAN controller telemetry
  Client experience telemetry
  Wi-Fi 6E/7 6 GHz surveying
  Walking coverage surveys

Kismet observations show what the sensor can receive at its location.

They do not automatically prove:

  Channel utilization
  airtime fairness
  AP CPU load
  controller load
  client count
  DHCP exhaustion
  WAN saturation

Correlate multiple data sources before assigning root cause.

38. REMOVE AGM WLAN CREDENTIALS
============================================================

List NetworkManager connections:

  nmcli connection show

Remove the temporary AGM connection:

  sudo nmcli connection delete "AGM-SSID"

Verify:

  nmcli connection show

If a dedicated credential file was created, remove it securely according
to organizational policy.

Do not include Wi-Fi passwords in the final survey report.


============================================================
39. TROUBLESHOOTING
============================================================

PROBLEM:

  USB adapter missing.

CHECK:

  lsusb
  dmesg | tail -100
  iw dev
  ip -br link


PROBLEM:

  Monitor mode cannot be enabled.

CHECK:

  ethtool -i wlan1
  iw list
  rfkill list

Confirm the chipset/driver supports monitor mode.


PROBLEM:

  Kismet sees no devices.

CHECK:

  iw dev
  rfkill list
  ip link show wlan1
  Kismet datasource status


PROBLEM:

  Active adapter connects but traffic uses Ethernet.

This is normal if Ethernet has the preferred default route.

The health script binds tests to wlan2 so Wi-Fi testing is still performed
through the active wireless adapter.


PROBLEM:

  Pi reboots or USB adapters disconnect.

Possible cause:

  Power supply or USB current limitation.

Use:

  Reliable Raspberry Pi power supply
  Powered USB hub if required


PROBLEM:

  Timestamps differ between devices.

CHECK:

  timedatectl
  chronyc tracking
  chronyc sources -v

40. RECOMMENDED FIELD WORKFLOW
============================================================

The overall procedure should be:

  1. Build Pi sensor.

  2. Test both USB Wi-Fi adapters.

  3. Test Kismet.

  4. Test active client measurements.

  5. Define survey locations.

  6. Arrive before delegates.

  7. Deploy fixed Pi sensors.

  8. Verify synchronized clocks.

  9. Perform WiFi Explorer Pro empty-room survey.

 10. Capture Pi baseline.

 11. Monitor through registration.

 12. Perform walking survey at attendance peaks.

 13. Timestamp all complaints.

 14. Correlate complaints with fixed sensor data.

 15. Investigate affected location with WiFi Explorer Pro.

 16. Record infrastructure actions.

 17. Export all logs after the event.

 18. Correlate Pi, Mac and infrastructure data.

 19. Produce AGM Wi-Fi findings and recommendations.

 20. Remove temporary WLAN credentials from sensors.


============================================================
41. DESIGN PHILOSOPHY
============================================================

Use WiFi Explorer Pro to answer:

  "What does the Wi-Fi environment look like HERE, NOW?"

Use the Raspberry Pi to answer:

  "What changed at this location over TIME?"

Use infrastructure monitoring to answer:

  "What was the WLAN/network infrastructure doing?"

Use the incident timeline to combine all three.

That combination is substantially more useful than an occasional
walk-through survey alone.

42. SOURCE NOTES
============================================================

Kismet installation documentation:

  https://www.kismetwireless.net/docs/readme/installing/linux/

Kismet package documentation:

  https://www.kismetwireless.net/packages/

Kismet documentation recommends using current packages where possible and
notes that modern Kismet compilation can be too resource intensive for a
Raspberry Pi 3. It also recommends limiting privileged operation to the
capture helpers rather than running the entire Kismet process as root.

Before deploying at an AGM, verify the exact Kismet repository and package
instructions for the Raspberry Pi OS/Debian release installed on the Pi.
