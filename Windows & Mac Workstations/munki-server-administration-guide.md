# Munki Server Administration

## Overview

Munki manages software on the organization's Mac fleet. It handles application
installs, updates, and removals without a user needing admin rights, and
without someone walking to each desk. The server side is simply a
web-served repository of packages and metadata; the client side is a set
of tools on each Mac that periodically check that repo and reconcile the
machine against what it has been told to have.

This guide covers the server: repo layout, how clients find it, adding a
package end to end, manifests, catalog promotion from testing to
production, and the failure modes that come up.

## How It Works

Munki has no agent daemon talking to a server API. It is a client-pull
model over plain HTTP(S):

```
Mac client (managedsoftwareupdate, on a schedule)
   -> HTTPS GET  <repo>/manifests/<client identifier>    # what should this Mac have?
   -> HTTPS GET  <repo>/catalogs/<catalog named in manifest>  # what is available, and what version?
   -> HTTPS GET  <repo>/pkgs/<installer path>            # download only what is needed
   -> installs / removes to reconcile the machine
```

The server is a **static file repository**. Any web server that can
serve files will do; there is no application to run, nothing to restart,
and no database. That simplicity is Munki's main virtue and also the
source of its main gotcha: **the catalogs are a generated cache, and
they do not update themselves.**

### Repo layout

| Directory | Contents | Notes |
|-----------|----------|-------|
| `pkgs/` | The actual installer files — .pkg, .dmg, .app archives | The bulk of the repo size. Subfolders are allowed and encouraged |
| `pkgsinfo/` | One plist per package: name, version, installer location, install checks, requirements | The metadata Munki actually reasons about. Editable text |
| `catalogs/` | **Generated** files merging all pkgsinfo entries per catalog | Never edit by hand. Regenerated by `makecatalogs` |
| `manifests/` | One plist per client or group: which catalogs to use, what to install/remove | Where policy lives |
| `icons/` | Application icons shown in Managed Software Center | Cosmetic but improves the user experience |
| `client_resources/` | Optional MSC branding/customisation | [FILL IN: in use?] |

The relationship in one sentence: **pkgsinfo describes packages,
`makecatalogs` compiles pkgsinfo into catalogs, and manifests tell a Mac
which catalogs to read and which items from them to install.**

### Catalogs vs manifests — the distinction that matters

- A **catalog** is a *menu*: the set of software available, and at what
  versions. `development`, `testing`, `production`.
- A **manifest** is an *order*: for this specific Mac or group, use these
  catalogs, and install these items from them.

A package in the `production` catalog is not installed anywhere until a
manifest names it. Adding a package to a catalog is safe. Adding it to a
manifest is what deploys it.

| Key | Purpose | Value here |

Read and set on a client:

```
defaults read /Library/Preferences/ManagedInstalls          # all current client settings
defaults read /Library/Preferences/ManagedInstalls SoftwareRepoURL   # just the repo URL
sudo defaults write /Library/Preferences/ManagedInstalls SoftwareRepoURL "[FILL IN: repo URL]"
sudo defaults write /Library/Preferences/ManagedInstalls ClientIdentifier "[FILL IN: manifest name]"
```

**How a client finds its manifest** — Munki tries, in order:

1. The `ClientIdentifier` value, if set.
2. The Mac's fully qualified hostname.
3. The Mac's short hostname.
4. The Mac's hardware **serial number**.
5. `site_default` — the catch-all manifest.

This fallback chain is useful: create a `site_default` manifest with the
baseline every Mac should have, and only create named manifests for
machines or groups that differ. **[FILL IN: does a `site_default`
manifest exist, and what is in it?]**

Where client state lives:

| Path | Contents |
|------|----------|
| `/Library/Managed Installs/manifests/` | Cached copy of the manifest this Mac received |
| `/Library/Managed Installs/catalogs/` | Cached copy of the catalogs |
| `/Library/Managed Installs/Cache/` | Downloaded installers awaiting install |
| `/Library/Managed Installs/ManagedInstallReport.plist` | Result of the last run |
| `/Library/Managed Installs/Logs/ManagedSoftwareUpdate.log` | The log to read when something is wrong |

## Operations (Day-2)

### Adding a Package — End to End

The established workflow is GUI-based through **MunkiAdmin.app**.
The original note is carried forward verbatim here because it contains
the two steps people actually get wrong:

> **Adding a package to Munki (original note)**
>
> Drop it onto the Desktop.
> Launch Munki Admin.
> Under Packages, choose **File → Import Items**.
> The pkginfo window will open. Most pkgs' default options are fine to
> leave as is. **Just make sure it's in the development Catalog.**
>
> **Key point:** Click **Save** after closing the pkginfo window (at the
> top, or **File → Save**).

Expanded into the full procedure:

**Step 1 — Obtain the installer**

Download the .pkg or .dmg from the vendor. Verify it is what you think it
is before it goes anywhere near the fleet:

```
shasum -a 256 ~/Desktop/[FILL IN: installer file]      # compare against the vendor's published checksum
pkgutil --check-signature ~/Desktop/[FILL IN: installer].pkg   # confirm a valid developer signature
spctl -a -vv /Applications/[FILL IN: app].app          # for .dmg/app payloads: notarisation check
```

Put it on the Desktop, per the original note — MunkiAdmin's import
expects a local file.

**Step 2 — Import via MunkiAdmin**

1. Launch **MunkiAdmin** and open the organization's repo. [FILL IN: MunkiAdmin
   needs the repo mounted or reachable locally — record exactly how the
   admin Mac reaches the repo, e.g. a mounted SMB share from
   files.example.com, or a local clone.]
2. Under **Packages**, choose **File → Import Items**.
3. Select the installer from the Desktop.
4. The **pkginfo** window opens.

**Step 3 — Review the pkginfo**

Defaults are usually fine. The fields worth a glance every time:

| Field | Why it matters |
|-------|----------------|
| **Catalogs** | **Set to `development` only.** This is the step the original note flags, and it is the one that prevents an untested package reaching production Macs |
| Name | Munki's internal item name. Keep it stable across versions — changing it breaks manifests that reference the old name |
| Display name | What users see in Managed Software Center |
| Version | Must sort correctly against the previous version, or clients will not see it as an upgrade |
| Minimum OS version | Set it if the app requires a newer macOS than some of the fleet runs |
| Installs array / receipts | How Munki decides the app is already installed. If this is wrong, Munki reinstalls forever or never installs at all |
| unattended_install | Allows installing without user interaction. Do not set it for installers that need a quit-the-app prompt |
| RestartAction | Set if the package genuinely requires a logout or restart |
| Category and icon | Cosmetic; makes MSC usable |

**Step 4 — Save (the step people miss)**

Close the pkginfo window, then **Save** — the toolbar button or
**File → Save**. MunkiAdmin holds changes in memory until you save.
Saving is what writes the pkginfo plist into `pkgsinfo/`, copies the
installer into `pkgs/`, and **runs `makecatalogs` for you**.

If you skip the save, nothing reaches the repo, and the package will
appear to have vanished. This is the most common "Munki lost my package"
report and it is always this.

**Step 5 — Verify it landed in the repo**

```
ls -lt [FILL IN: repo path]/pkgs/ | head             # installer copied in?
ls -lt [FILL IN: repo path]/pkgsinfo/ | head         # pkginfo written?
grep -c "[FILL IN: item name]" [FILL IN: repo path]/catalogs/development   # present in the development catalog?
```

**Step 6 — Test on a test Mac**

Put the item in a test manifest that uses the `development` catalog, then
force a check-in on the test machine (see below). Confirm:

- [ ] It downloads and installs without user interaction, if it is meant
      to be unattended.
- [ ] The app launches and works.
- [ ] A second `managedsoftwareupdate` run reports **nothing to do** —
      if Munki wants to install it again, the `installs` array or
      receipts are wrong. Fix that now; it will otherwise reinstall on
      every check-in forever.
- [ ] Any required restart behaves as expected.

**Step 7 — Promote**

Once tested, promote through catalogs — see Catalog Promotion below.

### Manifest Strategy — Groups vs Individual Machines

Do the work in **group manifests**, not per-machine ones. A fleet
managed by fifty individual manifests is a fleet nobody can reason about.

The pattern that scales is nested manifests: a per-machine manifest that
contains almost nothing except an `included_manifests` reference to the
groups it belongs to.

```
site_default                      # baseline every Mac gets
  |
  +-- included_manifests: core_software        # browser, security agent, utilities
                                               # everything below adds to this

group_[FILL IN: department]       # e.g. group_finance, group_admin
  +-- included_manifests: site_default
  +-- managed_installs: [department-specific apps]

[FILL IN: machine identifier]     # a specific Mac, only when it genuinely differs
  +-- included_manifests: group_[department]
  +-- managed_installs: [the one thing unique to this machine]
```

Manifest keys and when to use each:

| Key | Effect | Use for |
|-----|--------|---------|
| `managed_installs` | Munki installs and keeps it installed and updated | Software the machine must have |
| `managed_uninstalls` | Munki removes it and keeps it removed | Deliberately banning software |
| `optional_installs` | Appears in Managed Software Center for the user to install on demand | Software some users want; avoids a manifest edit per request |
| `managed_updates` | Updated if present, but not installed if absent | Things installed by other means that should still be patched |
| `included_manifests` | Pulls in another manifest wholesale | The nesting above |
| `catalogs` | Which catalogs this manifest may draw from | Set on group manifests; this is how a test group gets the testing catalog |

Guidance:

- **Use `optional_installs` generously.** Most "can you install X for me"
  tickets become self-service, and the user gets it without waiting.
- Put the `catalogs` array on the group manifest, so moving a machine
  between testing and production is a matter of which group it is in.
- Name manifests predictably. [FILL IN: record the naming convention —
  hostname-based, serial-based, or department-based.]

### Catalog Promotion: development → testing → production

Catalogs are the safety mechanism. A package moves through them as
confidence increases; the fleet only ever sees the last one.

| Catalog | Who uses it | Purpose |
|---------|-------------|---------|
| `development` | The admin's own test Mac only | Freshly imported, not yet tried. Where every package starts, per the import note |
| `testing` | A small pilot group — [FILL IN: which machines are in the pilot group?] | Real users, real work, small blast radius |
| `production` | The rest of the fleet | Tested and trusted |

[FILL IN: confirm the actual catalog names in use — this three-stage
naming is the Munki convention and matches the "development" catalog
named in the import note, but verify `testing` and `production` exist
and are named that way in this repo.]

**Promotion procedure:**

1. **development → testing**, after the package installs cleanly on the
   admin test Mac and a second run reports nothing to do.
   ```
   # MunkiAdmin: Packages -> select the item -> Catalogs -> tick 'testing'
   #   Leave 'development' ticked too, or untick it — either is fine, be consistent
   # Then: File -> Save    (this writes the pkginfo AND runs makecatalogs)
   ```
2. **Soak in testing.** [FILL IN: agree a soak period — a week is a
   reasonable default — and record it here.] Watch for reports from the
   pilot group. No news is the expected result.
3. **testing → production**, once the soak passes.
   ```
   # MunkiAdmin: Packages -> select the item -> Catalogs -> tick 'production'
   # Then: File -> Save
   ```
4. **Add it to the relevant manifest** if it is meant to be installed
   rather than merely available. Promotion alone deploys nothing — a
   manifest must name the item.
5. **Retire the old version.** Once the new version is in production and
   stable, untick `production` on the superseded pkginfo so clients stop
   being offered it. Keep the pkginfo and installer around for a while
   in case a rollback is needed — deleting it is the last step, not the
   first.

**Rolling back:** untick `production` on the bad version and re-tick it
on the previous one, then save. Clients pick up the change on their next
check-in. This is why old versions are worth keeping in the repo.

### makecatalogs — and when to run it

`makecatalogs` reads every plist in `pkgsinfo/` and regenerates the files
in `catalogs/`. **Catalogs are a cache. Nothing a client sees changes
until makecatalogs runs.**

```
makecatalogs [FILL IN: repo path]      # regenerate all catalogs from pkgsinfo
```

**Run it after any change to pkgsinfo:**

| Action | Needs makecatalogs? |
|--------|---------------------|
| Imported a package via MunkiAdmin and saved | No — MunkiAdmin runs it for you on save |
| Changed a catalog assignment in MunkiAdmin and saved | No — same |
| Edited a pkginfo plist by hand in a text editor | **Yes** |
| Deleted a pkginfo file directly from `pkgsinfo/` | **Yes** |
| Copied pkgsinfo files in from elsewhere | **Yes** |
| Edited a manifest | **No** — manifests are read directly, never compiled |

That last row is worth remembering in both directions: manifest changes
take effect on the next client check-in with no server-side step, while
pkgsinfo changes made outside MunkiAdmin do nothing at all until
`makecatalogs` runs.

`makecatalogs` also validates as it goes. Read its output — it reports
pkginfo entries that reference a missing installer, and duplicate
name/version pairs. Both are real problems worth fixing when it tells
you about them.

### Forcing a Client Check-In

Munki normally checks in on its own schedule (roughly hourly, via a
LaunchDaemon). To force it:

```
sudo managedsoftwareupdate                          # check only — reports what WOULD happen
sudo managedsoftwareupdate --installonly            # install what is already downloaded
sudo managedsoftwareupdate --checkonly              # explicitly check only, no install
sudo managedsoftwareupdate --munkipkgsonly          # skip Apple software updates
sudo managedsoftwareupdate -vvv                     # very verbose — use this when diagnosing
```

Best practice when testing a new package: run the plain check first and
**read what it says it will do** before letting it act.

Remotely:

```
ssh [FILL IN: admin account]@<mac-host> "sudo managedsoftwareupdate -vvv"
```

Users can also open **Managed Software Center** and click Check Again,
which is the right thing to tell them to do rather than talking them
through Terminal.

Clear the client cache and start clean when a machine is behaving
strangely:

```
sudo rm -rf "/Library/Managed Installs/Cache/"*        # discard downloaded installers
sudo rm -rf "/Library/Managed Installs/catalogs/"*     # discard cached catalogs
sudo managedsoftwareupdate -vvv                        # re-fetch everything
```

This is safe — all of it is a cache and is re-downloaded.

## Troubleshooting

### Symptom: A client is not updating — nothing installs, no errors visible

- Check, on the client, in this order:
  ```
  sudo managedsoftwareupdate -vvv                       # run it manually and WATCH the output
  tail -100 "/Library/Managed Installs/Logs/ManagedSoftwareUpdate.log"
  defaults read /Library/Preferences/ManagedInstalls     # is SoftwareRepoURL right? ClientIdentifier?
  curl -sI "[FILL IN: repo URL]/catalogs/production"     # can this Mac reach the repo at all? expect 200
  ls -l "/Library/Managed Installs/manifests/"           # did it actually receive a manifest?
  sudo launchctl list | grep -i munki                    # is the check-in LaunchDaemon loaded?
  ```
- Likely causes and fixes:
  - **Repo unreachable** — DNS, network, web server down, or the Mac is
    off the network. The `curl` above settles it in one step.
  - **Wrong or missing manifest** — Munki fell through to `site_default`
    or found nothing. Check the `ClientIdentifier` against the manifest
    names that actually exist.
  - **The item is in a catalog the manifest does not use** — e.g. the
    package is in `testing` but the manifest only lists `production`.
    Very common, and invisible unless you look.
  - **The item is in the catalog but not in any manifest** — promotion
    without deployment. Add it to the manifest.
  - **LaunchDaemon not loaded** — the Mac will never check in on its
    own. Reinstall munkitools on that client.
  - **Munki thinks it is already installed** — the pkginfo `installs`
    array matches something already present. Check the verbose output;
    it says so explicitly.

### Symptom: A package fails to install on clients

- Check:
  ```
  sudo managedsoftwareupdate -vvv                        # the actual installer error appears here
  tail -200 "/Library/Managed Installs/Logs/ManagedSoftwareUpdate.log"
  sudo installer -pkg "/Library/Managed Installs/Cache/[FILL IN: pkg]" -target / -verbose
  #   ^ installs the cached package by hand — isolates Munki from the installer itself
  ```
- Likely causes:
  - **Installer needs the app to be closed** and it is running. Set
    `blocking_applications` in the pkginfo so Munki waits rather than
    failing.
  - **Marked `unattended_install` but the installer is interactive.**
    Unset it.
  - **Minimum OS version not met** — Munki will skip, and say so.
  - **Download corrupt or truncated.** Clear the cache and retry:
    ```
    sudo rm -rf "/Library/Managed Installs/Cache/"*
    sudo managedsoftwareupdate -vvv
    ```
  - **Insufficient disk space** — Munki checks and refuses; the log says
    so plainly.
  - **Wrong `installs` array** causing an endless reinstall loop: Munki
    installs successfully, then next run decides it is still missing.
    The fix is in the pkginfo, not the client. Correct it, save in
    MunkiAdmin, and let clients pick it up.

### Symptom: Catalog not refreshing — a change on the server does not reach clients

- Likely cause, in order of probability:
  1. **`makecatalogs` was not run** after a hand edit to pkgsinfo.
  2. **MunkiAdmin changes were not saved** — see the import note's key
     point. Unsaved changes are not in the repo.
  3. A caching proxy or CDN between client and repo is serving stale
     catalogs.
  4. The client is using a cached catalog because it could not reach the
     repo.
- Check:
  ```
  # On the server:
  ls -l [FILL IN: repo path]/catalogs/                  # are catalog mtimes recent?
  grep -c "[FILL IN: item name]" [FILL IN: repo path]/catalogs/production
  makecatalogs [FILL IN: repo path]                      # regenerate and read the output for errors

  # On the client:
  curl -s "[FILL IN: repo URL]/catalogs/production" | grep -c "[FILL IN: item name]"
  #   ^ if the server has it and this does not, something is caching
  ls -l "/Library/Managed Installs/catalogs/"            # is the client's cached copy stale?
  ```
- Fix: run `makecatalogs`, confirm the item appears in the served
  catalog via `curl`, then clear the client cache and re-run:
  ```
  sudo rm -rf "/Library/Managed Installs/catalogs/"*
  sudo managedsoftwareupdate -vvv
  ```

### Symptom: Managed Software Center shows nothing, or is empty for the user

- Check: the manifest has `optional_installs` entries, and those items
  are in a catalog the manifest lists. An empty MSC almost always means
  the manifest has only `managed_installs` (which are not user-visible
  as choices) and no optional items.
- Also check the client received a manifest at all:
  ```
  ls -l "/Library/Managed Installs/manifests/"
  defaults read /Library/Managed\ Installs/ManagedInstallReport.plist   # last run's result
  ```

### Symptom: Munki wants to reinstall the same thing on every check-in

- Cause: the pkginfo's `installs` array or receipt check does not match
  what the installer actually puts on disk — a version string mismatch,
  or a path that does not exist post-install.
- Check the verbose output; Munki states which `installs` item it
  considers missing.
- Fix in the pkginfo (MunkiAdmin → Packages → item → Installs), then
  save. **Catch this during Step 6 testing**, before promotion — it is
  the reason the "second run reports nothing to do" check is in the
  procedure.

  immediately, but it is one for patching.
