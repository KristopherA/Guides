    Alright — this is one of those things that sounds risky but can absolutely be done cleanly if you prepare properly.

Below is a production-safe, zero-downtime SSL certificate rotation procedure for MySQL. This assumes:
	•	MySQL 5.7+ or 8.0
	•	TLS already enabled
	•	You are replacing certs signed by a CA (not switching to an entirely new trust model)
	•	Clients verify the server certificate (best practice)

If you’re doing this in production, test it in staging first. Always.

⸻

✅ Goal

Replace MySQL SSL/TLS certificates without restarting MySQL and without interrupting active connections.

⸻

🔎 Key Concept (Read This First)
	•	Existing connections keep using the old SSL context.
	•	New connections use the new certificate after reload.
	•	MySQL supports dynamic TLS reload via:

ALTER INSTANCE RELOAD TLS;

This is the critical piece that allows zero downtime.

⸻

🧭 High-Level Strategy
	1.	Generate new certs
	2.	Install them alongside existing ones
	3.	Validate permissions and paths
	4.	Reload TLS in MySQL
	5.	Confirm new connections use new cert
	6.	Remove old certs later (optional cleanup)

⸻

🛠 Step-by-Step Procedure

⸻

Step 1 — Verify Current SSL Configuration

Log into MySQL:

SHOW VARIABLES LIKE '%ssl%';
SHOW STATUS LIKE 'Ssl_server_not_after';

Confirm:
	•	ssl_cert
	•	ssl_key
	•	ssl_ca

Example expected output:

ssl_cert = /etc/mysql/ssl/server-cert.pem
ssl_key  = /etc/mysql/ssl/server-key.pem
ssl_ca   = /etc/mysql/ssl/ca.pem

Also confirm TLS is active:

SHOW STATUS LIKE 'Ssl_cipher';


⸻

Step 2 — Generate New Certificate Files

Generate new:
	•	server-cert.pem
	•	server-key.pem
	•	(Optional) updated ca.pem

Do not overwrite the live files yet.

Instead create:

server-cert-new.pem
server-key-new.pem


⸻

Step 3 — Set Correct Permissions

This is where people break production.

chown mysql:mysql server-*.pem
chmod 600 server-key-new.pem
chmod 644 server-cert-new.pem

If permissions are wrong, reload will fail silently.

⸻

Step 4 — Replace Files Atomically

Now swap them safely:

mv server-cert.pem server-cert-old.pem
mv server-key.pem server-key-old.pem

mv server-cert-new.pem server-cert.pem
mv server-key-new.pem server-key.pem

⚠ Do not change filenames if your my.cnf points to specific names.

Atomic rename avoids partial reads.

⸻

Step 5 — Reload TLS (No Restart)

Now inside MySQL:

ALTER INSTANCE RELOAD TLS;

If successful, no output (or OK message).

This does not disconnect clients.

⸻

Step 6 — Validate the New Certificate is Active

Open a new MySQL client connection and check:

SHOW STATUS LIKE 'Ssl_server_not_after';

Confirm expiration matches new cert.

Or from shell:

openssl s_client -connect mysqlserver:3306 -starttls mysql

Check certificate details.

⸻

Step 7 — Monitor for Errors

Check MySQL error log:

tail -f /var/log/mysql/error.log

Look for:
	•	SSL errors
	•	Permission denied
	•	TLS initialization failures

⸻

Step 8 — Cleanup (After Validation)

Once you’re confident everything is working:

rm server-cert-old.pem
rm server-key-old.pem


⸻

🚨 If You Are Rotating the CA

If you’re also changing the CA:

You must:
	1.	Deploy new CA to all clients first
	2.	Configure MySQL to trust both old + new CA temporarily
	3.	Then rotate server cert
	4.	Then remove old CA later

Otherwise clients will fail verification.

This is where most outages happen.

⸻

🔄 Optional: Zero-Risk Phased Approach (Enterprise Safe)

If you’re running replication or clustering:
	1.	Rotate replicas first
	2.	Failover
	3.	Rotate primary
	4.	Fail back (if needed)

This eliminates any risk at the primary layer.

⸻

🧪 Pre-Change Checklist

Before touching production:
	•	Confirm MySQL version supports ALTER INSTANCE RELOAD TLS
	•	Backup current cert files
	•	Validate new cert with openssl verify
	•	Confirm private key matches cert:

openssl x509 -noout -modulus -in server-cert.pem | openssl md5
openssl rsa  -noout -modulus -in server-key.pem  | openssl md5

Hashes must match.

⸻

⚠ Common Mistakes That Cause Outages

Mistake	Result
Wrong file permissions	TLS reload fails
Overwriting files before ready	MySQL loads broken cert
Not updating clients during CA change	All connections fail
Forgetting to reload TLS	New cert not used


⸻

📌 Quick Version (Minimal Downtime Command Summary)

# Place new certs
mv server-cert.pem server-cert-old.pem
mv server-key.pem server-key-old.pem
mv server-cert-new.pem server-cert.pem
mv server-key-new.pem server-key.pem

ALTER INSTANCE RELOAD TLS;

Done.

⸻

🧠 Final Advice (From Experience)

If this is production:
	•	Do it during low traffic window anyway.
	•	Have console access.
	•	Keep old cert files until verified.
	•	Test from a remote client after reload.

Zero downtime is possible — but only if you’re disciplined.
